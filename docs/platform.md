# Platform integration: KDE Wayland, Linux mouse shortcuts, Windows windows, game controllers

Read before changing `src-tauri/src/platform/`, `gamepad.rs` or the KWin script. Moved from AGENTS.md on 2026-11-11; keep it current in the same commit as the change it describes.

- **Mouse-button shortcuts on Linux (`platform/linux_mouse/`, 2026-11-11, at the user's request; X11 and every Wayland desktop, KDE Plasma 6 first):** the mice's event devices are read directly (evdev, raw libc ioctls, no new crate), because no portal, KWin script or XInput2 can keep a global click from the program under the pointer. Same settings as Windows (`mouseHotkey`: button, Alt/Ctrl/Shift matched exactly, `longPress` 450 ms keeping the click) plus `blockClick` (default true; Windows' hook ignores it and always swallows a click). The logic is `platform/mouse_hotkey.rs` (`Machine`, `Filter`, `RepeatGuard` 200 ms against one press seen on two nodes), tested without devices.
  - One thread (`linux_mouse::run`) polls the mice that have the button, an inotify on /dev/input (plug, unplug, renumbering by inode, permission changes) and an eventfd for new settings and stop; the long press is the poll timeout, no busy loop. Keyboards are opened only when the shortcut's button goes down, and only asked their state (EVIOCGKEY), never read; without keyboard access a shortcut with keys does not fire and the status says so.
  - Watching (read access only): the lookup fires and the click still reaches the program. Blocking (click mode, `blockClick`, /dev/uinput writable, a mouse with only SYN/KEY/REL/ABS/MSC): a uinput copy of the mouse is made (its name, ids, capabilities, phys `lookitan/mouse-hotkey`, which is how our copies are never read), and the mouse is grabbed (EVIOCGRAB) only after another process is seen to have the copy's node open (`opened_elsewhere`, /proc/*/fd; up to 3 s, else it stays watching with a note) and with no button held (a press the desktop saw must reach it released). A write to the copy that fails lets go of the copy's buttons, ungrabs and goes back to watching; touchpads, tablets and other programs' grabs (EBUSY) are never taken; the kernel drops the grab and the copy if Lookitan dies; `stop()` on quit.
  - Permission (`setup.rs`): only from the user's click in Configurações › Atalhos › "Acesso ao mouse": pkexec runs one fixed /bin/sh script (`SCRIPT`) with the rule text as `$1`, writing `/etc/udev/rules.d/70-lookitan-input.rules` (refuses a file it did not write), `udevadm` reload/trigger, and on narrowing or removal `setfacl -x` of the parts dropped. The rule is `TAG+="uaccess"` per class: mice always, keyboards and uinput only when ticked (each with its risk said). No `input` group, no MODE, Lookitan never runs as root. "Comandos para o terminal" gives the same as sudo commands. Packages ship no rule. Commands `mouse_hotkey_status`, `mouse_hotkey_setup`, `mouse_hotkey_commands`.
  - Not tested on hardware by an agent (CI has no input devices): grabbing and the copy are covered by an `#[ignore]` uinput test (`mouse_backend_reads_a_fake_mouse…`), to run by hand with the permissions.
- **Floating windows on Windows:** `platform::win::keep_tool_window` makes the overlay and the pop-up tool windows (`WS_EX_TOOLWINDOW`, no `WS_EX_APPWINDOW`), as Lookupper's are.
  - Chromium's occlusion tracker stops drawing a browser window that other windows seem to cover fully, which made a video under the whole-screen overlay go black. `gfx::IsWindowVisibleAndFullyOpaque` ignores tool windows.
  - tao rewrites the extended style on state changes. A `SetWindowSubclass` handler for `WM_STYLECHANGING` keeps the bit.
  - Linux has no such tracker; the user checked that videos stay visible there.
- **KDE Wayland:**
  - The cursor comes from the KWin script over D-Bus (`io.github.arrowpoppa.Lookitan` `/Cursor`).
  - Capture uses `org.kde.KWin.ScreenShot2.CaptureArea`, which is authorized only when Lookitan runs from the installed `.desktop` entry.
  - The windows run under XWayland.
  - On Wayland, the global shortcut is a system shortcut that runs `lookitan --scan`.
- **Game controllers (gamepad.rs, `settings.gamepad`, Configurações › Atalhos › Gamepad):** Lookupper (REA on 2026-10-23: `XInputPoller` over xinput1_4.dll, a raw-HID `HidGamepadListener`, `GamepadCombination`, `GamepadOverlayNavigation`, `OnGamepadNavigate/Scroll/Action`, `DismissTopmost`, `WaitForGamepadReleaseAsync`, an injected `lookupper-gp-focus` outline) looks up with a combination of buttons and, with navigation on, moves a focus outline. Lookitan clones that behavior:
  - Input: gilrs 0.11 with only its `xinput` backend on Windows (WGI would need the window focused), evdev on Linux (needs `libudev-dev` to build; the seat's uaccess rule gives read access to joysticks). PlayStation pads (DualSense, Edge, DualShock 4) on Windows are read from their HID reports (`gamepad/playstation.rs`, hidapi `windows-native`, from Harbor, arrow-poppa/streaming, MIT, without its touchpad): USB, the long Bluetooth report if another program switched to it, and the short one, which Lookitan never asks to switch (that would change what other programs get). Other non-XInput pads on Windows still need Steam. On Linux, buttons and axes gilrs has no mapping for are read by their standard evdev codes (`raw_event`, Harbor's table), and a D-pad reported as a hat counts as the D-pad. All sources are merged into one set of held buttons, so a pad seen twice (DS4Windows) does not double anything. One thread polls every 16 ms; `Machine` (tested without a controller) turns the held buttons into `Signal`s.
  - `hotkey` (Xbox names, `gamepad::BUTTONS`) fires `scan` once when all are held; nothing navigates until every button is released. The settings box records a combination with `gamepad_capture(true)`: every button seen until all are let go (`gamepad-capture` events), empty after 10 s with nothing pressed.
  - `navigation` (on by default, like Lookupper): only while the pop-up or overlay is visible (`gamepad_target`). D-pad or left stick (past 0.6, repeat after 400 ms then every 120 ms) moves; the right stick scrolls `#sections`. With the pop-up up, it moves between its visible controls (`nearest` in src/lib/gamepad-nav.js, a sideways step counting twice) and `confirm` clicks the outlined one, `close` closes the picture viewer or saved cards first, then only the pop-up (`popup_dismiss`, the overlay stays), `save` clicks the bookmark, `pronounce` the first ouvir button. With only the overlay, it moves between the words from the word looked up and `confirm` looks the outlined word up (`overlay_pick`); `close` closes the lookup.
  - Button names follow the connected pad (`src/lib/gamepad-buttons.js`): a PlayStation pad's name shows ✕ ○ □ △, L1/R1/L2/R2, Options/Create; settings always store the Xbox names.
  - Actions (`confirm`, `close`, `save`, `anki`, `pronounce`, `explain`, `meme`; A, B, X, LB, Y, RB by default, `meme` none; `meme` clicks the Imagens section's "Modo meme" switch, or flips the setting when it is not showing) each take one button or several held together (`Vec<String>`; settings saved by the first build as one name are read as a list of one). `explain` clicks the pop-up's "Explicar" (`.explain-word`) and `anki` its Anki button, both beyond Lookupper, as the user asked. An action fires when its buttons are all held; when several complete at once, only the longest. An action whose buttons are inside a longer binding (the look-up combination counts) waits for release and fires only if no other button joined (`Machine::pending`); the look-up combination cancels it. A direction held as part of an action does not move. A combination another action has swaps with it.
  - Configurações › Atalhos › Gamepad folds like Lookupper's row (`collapser('gamepad')`, chevron beside the look-up box): the navigation switch with a legend of the bindings, then one recording box per action, with × to leave it empty and ↺ to put the default back.
