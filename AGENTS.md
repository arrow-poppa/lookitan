## What this is

Lookitan is a pop-up dictionary for Windows and Linux. The user points at a word anywhere on screen and presses a shortcut. OCR reads the screen, and a pop-up shows MDict entries and AI cards.

- It reproduces the *behavior* of Lookupper, a Windows-only app.
- The AI layer is "bring your own key" (BYOK). It is ported from `arrow-poppa/yomitan-byok-ai`, branch `feature/byok-ai-explanations`.
- License: GPL-3.0-only. Third-party credits are in `NOTICE.md`.

The user is on **Fedora with KDE Plasma on Wayland**. Linux, KDE Wayland and the `.rpm` package are first-class targets. The UI text is in Portuguese (pt-BR).

## Hard constraints

- **Behavior clone only.** Never copy Lookupper's decompiled code, assets, branding, UI text or servers (`gateway.lookupper.com` and the others).
- **Google Lens key:** never in the source (OneOCR's model key, `onemodel::KEY` in ocr/onemodel.rs, is no service key: it is the fixed string the library opens its own model file with, published in oneocr and owocr; added on 2026-10-28 with the engine the user asked for, and since 2026-10-31 also what decrypts the user's imported `oneocr.onemodel` on Linux). Builds get it from the GitHub Actions secret `LOOKITAN_LENS_API_KEY` (Chromium's public Lens key, as owocr and chrome-lens-ocr send it), read at compile time with `option_env!` in ocr/lens.rs, at the user's request on 2026-10-21. It still ends up inside the binary. A key the user pastes in Settings › OCR is sent instead; a build without the secret (local, a fork's pull request) needs the user's key. Never embed any other key.
- **No local Rust builds.** The user's PC has little RAM. Rust compiles and installers come from GitHub Actions only. Locally, `npm run build` (Vite) and `npm test` are fine.
- **Never put the user's email in commits, requests or files.** Commits use the GitHub noreply address set in the repo's local git config.
- **Installers:** Windows ships the NSIS `.exe` only, with no `.msi`. Linux ships `.deb`, `.rpm` and `.AppImage`.

## Key behavior

- **Local dictionaries (0.2):** see `docs/dictionary-engine.md` for formats, evidence and limits.
  The settings wire tag `kind: mdict` is retained for all local readers to keep existing settings
  compatible; `DictInfo.format` identifies the actual format. Do not use this tag to infer file format.
  **Storage follows Lookupper's model (user's decision, 2026-10-15): no database.** Importing a ZIP
  unpacks it into `<local data>/dictionaries/content/<id>/` (`source::install`; ZIP, RAR, 7z, TAR or gz/bz2/xz, `dictionaries/archive.rs`), and the files are
  read from there unchanged; removing the dictionary deletes that copy. A main file chosen directly
  is read in place. MDict reads its own key index on every open (no sidecar). Every other format
  keeps a headword index beside its files, `<main>.lkidx` (`dictionaries/lkidx.rs`: Lookupper's
  HeadwordIndex layout plus each entry's offset/length in the source; in the app cache for a file
  used in place), and renders the entry from the source bytes at lookup time: Yomitan
  (`yomitan.lkidx`, `dictionaries/yomitan.rs`) and the rest in `dictionaries/inplace.rs`, which
  re-runs the format's reader over the entry's span. `.dz` is read by chunk (`dictzip.rs`); plain
  gzip/bzip2 lexicon files are unpacked once into the cache. There is no SQLite any more. Lookupper's formats: mdict, yomitan, stardict, slob, dsl, cc-cedict, gcide,
  webster-text, wordnet-lmf-xml, jmdict-simplified-json, kanjidic2-json, kaikki-jsonl; Codex's
  other readers stay as extras. All
  source/AI sections follow one configured popup order. Anki retains all homographs per source.
  MDict block caches are bounded by bytes; do not restore a count-only cache. Imports/loads are
  serialized in AppState, with atomic index publication and safe ZIP extraction. Cleanup at start
  deletes only `.unpacking-*` folders and copies marked `.lookitan-removed`, never unmarked ones.
  Morphology uses the OCR language. Order of forms: on-screen spelling, then Hunspell stems
  (Lookupper's de/en/es/fr/pt/ru plus every other recognition language with a wooorm/dictionaries
  package: bg cs da el hr hu it la nb nl pl ro sk sl sr sr-latn sv tr uk; Bosnian uses hr; ar is AyaSpell from LibreOffice's dictionaries; fi and id have none;
  `dictionaries/hunspell.rs`; files in `resources/hunspell/` from
  `fetch-assets.py`, one language loaded at a time), then Yomitan rules for ja, en, es, ar, uk
  and de (zu-infinitive only; `data/*-yomitan.json` from yomidevs/yomitan d3c54c1, Arabic and
  some Ukrainian rules carry Yomitan's pattern, run with fancy-regex), German ge…t/ge…en
  participles written in morphology.rs, WordNet EN exceptions and conservative PT rules. Original Lookupper language packs/algorithms are not copied.
  Run reader tests on GitHub Actions (`dictionary-engine` / `scripts/dictionary-harness`), never
  compile Rust locally. Dependency lockfile resolution without compiling is allowed.

  - Pairs (`0x140959e80`): lines sorted by centre; each line with the nearest line below it that runs the same way, overlaps it across by ≥ 0.2 × the narrower width (or 3 px), and is at most 2.2 × the smaller height down.

    - Ink (`0x140954000`): Otsu on the line's box, the smaller side is the ink. The ink height is the shortest run of rows holding 85% of it, and its colour is the mean under it.
    - Frames (`0x140954ac0`): around all lines (2.5 line heights out, shrunk to ≤ 800 px), grey, 3 × 3 median, Scharr across and down (CV_16S), absolute, added, over 40. Edge parts mostly inside the lines' boxes or shorter than 1.2 line heights are dropped. The rest, inverted and median-filtered, gives 8-connected parts. A line's frame is the part filling most of its box (parts ≥ max(16, 4 h²)), if that part holds the box; it is "filled" at ≥ 60% and "small" under half the area. These are OpenCV calls in Lookupper (REA named each P/Invoke: `imgproc_Scharr`, `imgproc_medianBlur`, `imgproc_connectedComponentsWithStats`…); Lookitan does them in Rust.

  - Regions (`0x140956b60`): a pair is linked when the gap ≤ 1.3 h (1.8 in one small frame), the overlap ≥ 0.45 × the narrower width, the size ratio ≤ 1.35 (1.6), and they are not in two different small frames. Links make runs top to bottom, cut where a step is > 1.3 × the median step and > median + 0.3 h.
  - Region kinds (`0x1409575c0`), in this order:
    - list-like when ≥ 85% of the cased lines start with a capital or a digit (not mostly all capitals, and not `early` < 0.3 with > 3 words);
    - framed when one small frame holds ≥ 70% of its lines, no line is in another small frame, and the text spans much of it;
    - prose when ≥ half the cased lines start in lower case;
    - centred when the centres vary < 0.6 × the ends;
    - list-like when its lines are short and spaced, or most have a short line level with them in a column to the right (`0x140958740`);
    - then by `early`, the share of lines ending short whose next first word would have fitted (`0x140958a80`): ≤ 0.25 prose, ≥ 0.35 list-like, else other.
  - Score (`0x140958b50`), joined under 1:
    - adds 5 for a list marker below; 7/4/1.5 for a size ratio over 1.7/1.45/1.3 (heights or ink heights); 3/1.5 for ink colours over 100/55 apart; 3 for two different filled frames, one small; 3.5 for a step over 1.35 × the region's; 5/3/1.5 for a gap over 1.6/1.1/0.8 h; 1.5 for different regions; 5 when neither has a letter; 1.5 for a sentence end then a capital or digit (outside prose); 2 for an ending colon; 3 for two "key: value" lines;
    - by region kind and how the upper line ends (reaches the edge / wraps / would have fitted): prose 0 / −3 / +0.5; list-like +1.5 / +1 / +3, plus 2.5 when its lines start with capitals; centred −1.5; framed −2.5; other +0.5 / +0.5 / +2.5;
    - takes 4 for an ending hyphen, 2.5 for a comma, 2.5 for an open bracket, 4 for a lower-case start below, 4 for a list item's next line at its text's indent, 3 for a CJK line ending in a particle.

- **Word edges (`ocr/ink.rs`), as in Lookupper's "word edges are snapped to the ink of the line":** the rules below are Lookitan's own. Lookupper's own, decoded on 2026-10-21 (REA, not ported):
  - Per line (`0x140949b60`): a line whose words are all CJK gives every character its own box, then the analyzer rejoins them. Otherwise each word is a box. Character boxes are centred on the CTC step, as wide as the mean character pitch, the full crop height; a word's box is the union of its characters'.
  - Ink (`0x14094de10`): the background is the mode of a 64-bin grey histogram (every 2nd column, 4th row). The contrast is where the outer 5% of pixels lie; it needs at least 24. A column's ink is the count of pixels further than 0.3 × contrast from the background, over the whole crop height.
  - Ink word split (`0x140950d00`, not for all-CJK or RTL lines, words of 4 to 64 characters): the blank run nearest the middle of each character pair is its gap. A word is cut where the gap is at least max(2.5 × the word's median gap, 0.75 × the line's median word gap, 0.15 × pitch, 0.25 × crop height), leaving pieces of 2 characters or more.
    - Ported on 2026-10-22: `ink::word_cuts` and `paddle.rs` `split_at_ink_gaps`, which puts a space at each cut, after `split_wide_gaps`.
    - Words there are runs of one class between spaces, CJK (`is_cjk_class`, Lookupper's `0x140950be0`) or not.
    - Only the non-CJK runs are cut; Lookupper's analyzer rejoins CJK characters across a space anyway.
    - RTL lines are left alone.
    - Lookitan's `ink.cols` count ink only in the line's ink rows, where Lookupper counts the whole crop height.
  - Snap (`0x14094da60`): between two neighbouring boxes, the best blank run within 0.4 × crop height of their meeting point (width − 1.2 × distance) becomes the boundary. The line's ends move to its first and last ink within that reach. Boxes that still overlap meet halfway (`0x14094a980`).
  - CTC gives each character only a step centre. `ink::measure` finds the crop's ink: pixels far from the median background, in the run of rows holding the most ink.
  - `ink::spans` moves each boundary between two characters to the widest blank gap between their centres, and the line's ends to its first and last ink. Spaces fill the gap between words.
  - `OcrLine.ink_y` holds the ink rows; word boxes and the pick use them (`text_rows` in words.rs).
  - Boxes keep a little room around the ink (`INK_PAD_Y` 12% of the ink height above and below, `INK_PAD_X` 8% at the sides), never past the detected line box, and neighbours that touch share the gap. Raise these two constants if the highlight still looks tight.
  - Drawn box and hit area are separate, so the tight box does not make words hard to hit. `WordBox.hit` (`OverlayWord.hit`, `[x, y, w, h]`) spans the line's whole detected height and reaches halfway to the neighbouring words, or 0.25 × line height past a line's ends. In the overlay, `.w` is that area and takes the clicks and the hover, and its `.ink` child (`pointer-events: none`) draws the highlight and the cut-out. The pointer mode never used these boxes.
  - `Pick::is_under` tests the drawn box, the same one the user sees highlighted. Before 2026-10-15 it reached a quarter of the line height past the word box, which then spanned the whole line height and half the spaces. That made the space between words and lines count as on a word, so the block outline almost never appeared.
  - With little contrast, under 40 levels, the old halfway estimates stay.
  - Google Lens lines are snapped too (`snap_to_ink` in ocr/lens.rs, since 2026-10-21): `ink::measure` on the line's box in the capture gives `ink_y`, and each word's ends move to its first and last ink column within 0.15 line heights of Lens's word box (`INK_REACH`), never past halfway to the next word. Vertical lines keep Lens's boxes.
