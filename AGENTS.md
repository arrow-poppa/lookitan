## What this is

Lookitan is a pop-up dictionary for Windows and Linux. The user points at a word anywhere on screen and presses a shortcut. OCR reads the screen, and a pop-up shows MDict entries and AI cards.

- It reproduces the *behavior* of Lookupper, a Windows-only app.
- The AI layer is "bring your own key" (BYOK). It is ported from `arrow-poppa/yomitan-byok-ai`, branch `feature/byok-ai-explanations`.
- License: GPL-3.0-only. Third-party credits are in `NOTICE.md`.

The user is on **Fedora with KDE Plasma on Wayland**. Linux, KDE Wayland and the `.rpm` package are first-class targets. The UI text is in Portuguese (pt-BR).

## Hard constraints

- **Behavior clone only.** Never copy Lookupper's decompiled code, assets, branding, UI text or servers (`gateway.lookupper.com` and the others).
- **Google Lens key:** never in the source. Builds get it from the GitHub Actions secret `LOOKITAN_LENS_API_KEY` (Chromium's public Lens key, as owocr and chrome-lens-ocr send it), read at compile time with `option_env!` in ocr/lens.rs, at the user's request on 2026-10-21. It still ends up inside the binary. A key the user pastes in Settings › OCR is sent instead; a build without the secret (local, a fork's pull request) needs the user's key. Never embed any other key.
- **No local Rust builds.** The user's PC has little RAM. Rust compiles and installers come from GitHub Actions only. Locally, `npm run build` (Vite) and `npm test` are fine.
- **Never put the user's email in commits, requests or files.** Commits use the GitHub noreply address set in the repo's local git config.
- **Installers:** Windows ships the NSIS `.exe` only, with no `.msi`. Linux ships `.deb`, `.rpm` and `.AppImage`.

## Key behavior

- **Local dictionaries (0.2):** see `docs/dictionary-engine.md` for formats, evidence and limits.
  The settings wire tag `kind: mdict` is retained for all local readers to keep existing settings
  compatible; `DictInfo.format` identifies the actual format. Do not use this tag to infer file format.
  **Storage follows Lookupper's model (user's decision, 2026-10-15): no database.** Importing a ZIP
  unpacks it into `<local data>/dictionaries/content/<id>/` (`source::install`; ZIP, RAR, 7z, TAR or gz/bz2/xz, `dictionaries/archive.rs`), and the files are
  read from there unchanged; removing the dictionary deletes that copy. A main file chosen directly
  is read in place. MDict reads its own key index on every open (no sidecar). Every other format
  keeps a headword index beside its files, `<main>.lkidx` (`dictionaries/lkidx.rs`: Lookupper's
  HeadwordIndex layout plus each entry's offset/length in the source; in the app cache for a file
  used in place), and renders the entry from the source bytes at lookup time: Yomitan
  (`yomitan.lkidx`, `dictionaries/yomitan.rs`) and the rest in `dictionaries/inplace.rs`, which
  re-runs the format's reader over the entry's span. `.dz` is read by chunk (`dictzip.rs`); plain
  gzip/bzip2 lexicon files are unpacked once into the cache. There is no SQLite any more. Lookupper's formats: mdict, yomitan, stardict, slob, dsl, cc-cedict, gcide,
  webster-text, wordnet-lmf-xml, jmdict-simplified-json, kanjidic2-json, kaikki-jsonl; Codex's
  other readers stay as extras. All
  source/AI sections follow one configured popup order. Anki retains all homographs per source.
  MDict block caches are bounded by bytes; do not restore a count-only cache. Imports/loads are
  serialized in AppState, with atomic index publication and safe ZIP extraction. Cleanup at start
  deletes only `.unpacking-*` folders and copies marked `.lookitan-removed`, never unmarked ones.
  Morphology uses the OCR language. Order of forms: on-screen spelling, then Hunspell stems
  (Lookupper's de/en/es/fr/pt/ru plus every other recognition language with a wooorm/dictionaries
  package: bg cs da el hr hu it la nb nl pl ro sk sl sr sr-latn sv tr uk; Bosnian uses hr; ar is AyaSpell from LibreOffice's dictionaries; fi and id have none;
  `dictionaries/hunspell.rs`; files in `resources/hunspell/` from
  `fetch-assets.py`, one language loaded at a time), then Yomitan rules for ja, en, es, ar, uk
  and de (zu-infinitive only; `data/*-yomitan.json` from yomidevs/yomitan d3c54c1, Arabic and
  some Ukrainian rules carry Yomitan's pattern, run with fancy-regex), German ge…t/ge…en
  participles written in morphology.rs, WordNet EN exceptions and conservative PT rules. Original Lookupper language packs/algorithms are not copied.
  Run reader tests on GitHub Actions (`dictionary-engine` / `scripts/dictionary-harness`), never
  compile Rust locally. Dependency lockfile resolution without compiling is allowed.

- **OCR:**
  - The detector tries det_small on the GPU first. If GPU inference fails, it releases the GPU session and retries on the CPU with det_tiny. Foreground and overlay OCR share that CPU session.
  - GPU first on both platforms (DirectML on Windows, WebGPU/Vulkan on Linux); the user runs Lookitan on Windows and on Fedora KDE. After a GPU failure the stage stays on the CPU until restart. A "retry the GPU on the next input" variant was tried in 5ab8870 and reverted at the user's request as less safe; do not reintroduce it without asking.
  - GPU card: off by default (`chooseGpu`), DirectML takes adapter 0 and Linux takes Dawn's default (high performance). With "Escolher a placa de vídeo" on, `gpuPreference` (`highPerformance`/`lowPower`) goes to DirectML's performance preference or to the WebGPU EP's `powerPreference`. The WebGPU `deviceId` is ONNX Runtime's context id, not an adapter index. The Linux packages depend on the Vulkan loader (`vulkan-loader`, `libvulkan1`).
  - The models are the same PP-OCRv6/PP-OCRv5 weights as Lookupper, from the official PaddlePaddle exports. Lookupper's copies are a different ONNX conversion (det at opset 11 instead of 14).
  - The detector follows Lookupper (REA: its defaults at `0x140949390` are WhitePadding 20, 1920 GPU, 1280 CPU, box score 0.8, line confidence 0.65; the detector lambda is `0x140951940`). The image is at most 1920 px on its longest side on the GPU and 1280 px on the CPU (`DET_MAX_SIDE_GPU`/`_CPU`), inside a 20 px white border (`DET_PADDING`). Binarization is 0.3 (Lookupper's 76/255), unclip 1.35, as Lookupper's. Lookupper also moves each grown box down by 0.15 × area / perimeter; Lookitan does not (1–2 px, no gain, removed at the user's request). Whole-screen OCR runs in overlapping bands. Not copied, at the user's request, because they lose faint words: Lookupper drops boxes under a mean score of 0.8 (Lookitan keeps 0.45 GPU / 0.4 CPU) and recognized lines under 0.65 confidence (`0x140947860`; Lookitan drops none).
  - Turned lines (branch `lookupper-ocr`, as Lookupper's contour lambda `0x140951940`): each detector kernel gets its smallest rectangle (`quad.rs`, from the hull of its rows' end corners). Turned more than 2° (`UPRIGHT_ANGLE`; Lookupper straightens every box, but below that the plain crop reads the same and keeps the ink rows), the box carries its corners (`TextBox::quad`, with `x0..y1` the bounds), unclipped by 1.35 × its own area / perimeter. Its crop is straightened (`quad::warp`, bilinear, edges repeated) before it is read, vertical by its own sides (`TextBox::size`), and the block's pointer test turns with it. The line comes out in its own frame (`OcrLine::tilt`: the capture turned by `-angle` about its origin): characters and ink there. words.rs reads it in that frame (`upright`, `upright_point`), and maps word boxes back with `turned_on_screen`: upright about their true centre, plus `angle`; the overlay turns each word element by it (`rotate(...rad)`, the ink child turning with it), `Pick::is_under` turns the pointer back, and the pop-up is placed by `Pick::bounds`. Paragraphs compare a turned line by its box on the capture, as Lookupper's analyzer does.
  - Wide gaps split words (branch `lookupper-ocr`, Lookupper's `0x14094c7a0`): in each recognized line, a gap between two characters wider than 2.5 × the line's median gap (in recognizer steps, clamped to 5..20, 8 with under two characters) gets a space (`split_wide_gaps`), so two labels or cells in one box are two words.
  - Recognition has two phases: the lines near the pointer first, one run per line, then the rest in the background for the overlay.
  - The background whole-screen pass is batched: `plan_batches` groups lines of similar width (at most 16 lines and 12,000 padded columns per run), pads them with zeros like PaddleOCR, and decodes each line only over its own CTC steps. A failed batch retries line by line.
- **Scan result:** the pop-up opens only when the pointer is on a word (`Pick::is_under`): inside the word's drawn box, give or take `UNDER_SLACK` (10% of the box height, at least `UNDER_SLACK_MIN` = 3 capture pixels). The space between words or lines is off any word. Otherwise the automatic capture outlines the block of text (block.rs: the pointer must be on a line, give or take 0.2 of its text size across it and 0.5 past its ends; the block grows through lines 0.6 text sizes apart that overlap, and pieces of a line 1.5 apart, of sizes within ×1.6, up to 40 boxes. These are Lookitan's own and read a whole block, where Lookupper's clustering `0x14094b8c0` reads part of it, which the user does not want. A column is measured by its width, with its axes swapped, so the columns beside it are its neighbouring lines. A block read as at most one letter or digit is dropped and every box is read, as Lookupper's `0x140947790`), and otherwise the scan re-captures the whole monitor and shows the focused overlay of clickable words with no pop-up, as Lookupper does. Also like Lookupper, that whole-screen overlay appears only after the background pass has read the whole screen (`deferred` in `run_scan`), not progressively; Right after the whole-screen capture, `show_overlay_window` raises the overlay transparent (body class `idle`, only the 0.01-alpha shade), so clicks and the scroll wheel cannot move the screen away from the captured frame while OCR runs; the words appear with the final `emit_overlay` (immediately on Linux, with a fade elsewhere). A click or Esc meanwhile cancels: `overlay_close` bumps `scan_seq`, which stops the background pass and makes `run_scan` return early. `Recognition::scan` keeps the overlay's move/resize handler from redrawing an older lookup while a new scan is under way. An empty click on the overlay calls `overlay_dismiss`: in a whole-screen lookup with the pop-up pinned ("Fixar"), it hides only the pop-up and keeps the words clickable, and the next empty click closes the overlay (Lookupper's behavior, which the user wants only when pinned). Otherwise it closes the overlay and the pop-up at once. Esc or X in the pop-up always closes both (`hide_popup`). The "Área lida" setting is gone: `migrate()` forces `ocrScope` to Region, and the capture-region size is always editable.
- **Pop-up placement (`popup_position` in lib.rs, both platforms):** WinUI's TeachingTip targeted placement, which is what Lookupper's lookup popup uses. That popup is `Lookupper.Lookups.Views.WordTeachingTip`, a UserControl holding a `TeachingTip` named `TeachingTipControl` (style `LookupTeachingTipStyle`). `OverlayView.AddWordTeachingTip` adds it to the full-monitor overlay, aimed at a rectangle on the word. Its XAML in `resources.pri` sets no `PreferredPlacement`. The algorithm was read from microsoft-ui-xaml `controls/dev/TeachingTip/TeachingTip.cpp` (`DetermineEffectivePlacementTargeted`, `GetPlacementFallbackOrder`, `PositionTargetedPopup`) on 2026-10-21:
  - Modes are tried in order, and the first whose fit test passes wins (`PLACEMENT_ORDER`). Top/Bottom need the card centred on the word to fit, so a word near a side gets Left or Right before any shifted variant (TopLeft…RightBottom). That is the user's "passou" screenshot.
  - Sizes from TeachingTip_themeresources.xaml: the card sits in a grid with an 8 px strip on every side (`TeachingTipTailShortSideLength`), and the 20×10 tail is drawn in the strip facing the word. So the card is 8 px from the word; Lookitan has no tail but keeps the gap. In the shifted variants the word's centre is 28 px from the grid edge (`MinimumTipEdgeToTailCenter` = 8 + 10 + 10), i.e. 20 px into the card. Bounds: the whole monitor (the overlay window). `ShouldConstrainToRootBounds` must be true, since with false WinUI always returns Top.
  - Open question: WinUI's Auto order starts with Top; a Bottom preference swaps Top and Bottom. Lookupper's code-behind could set either, and the screenshots so far fit both. Lookitan keeps Bottom first, as before. Check by looking up a word in Lookupper with room both above and below.
  - Where WinUI would not open the tip at all, Lookitan still shows it, centred below or above and kept on the monitor.
- **Freeze:** per app, as in Lookupper: each profile in Configurações › Jogos e programas has `freeze` = `none` ("Sem congelar", the default: the screen stays live and only the words are highlighted), `frame` ("Congelar": the captured frame covers the screen; on whole-screen lookups it is blurred with sharp word cut-outs) or `process` ("Pausar o programa"). There is no global freeze option; the short-lived `freezeOnLookup` key is ignored, and `migrate()` turns saved `default` profiles into `none`.
- **Sentence:** like Lookupper, the context is the word's paragraph, and `Pick.sentence` is the sentence cut from it.
- **Words of other scripts and right-to-left text (words.rs, ocr/mod.rs `reverse_rtl`), as in Lookupper (REA on 2026-10-21):**
  - A word is a run without a space, cut where unspaced-script text starts or ends, trimmed at its ends of what is not a letter or digit ("(U.S.A.)," → "U.S.A"), or kept whole when nothing would be left, so punctuation alone ("？", "—", "。") is a word with its own box and pick, as Lookupper's `GetTrimmedWordAndRect` (`0x14015e6c0`) does; the analyzers' punctuation tokens are words too, as in its resegmenter. Only a space is off any word. Punctuation inside stays ("end.Next"); its pieces are tried too, the one under the pointer first.
  - A paragraph with no letter and no digit ("— •"), or of a single Latin or Cyrillic letter, is noise: no word boxes, no pick (Lookupper's `IsNoiseParagraph`). Lookupper also drops a paragraph of digits; the user chose to keep any paragraph with a digit, so a number alone can be looked up.
  - A line-end hyphen (-, U+2010, U+2011) after a letter joins the next line's word when that starts lowercase, or uppercase after a word with no lowercase ("EXAM-" "PLE"). The test is `char.IsLower` in Lookupper's `Any` call.
  - Right-to-left: a line with more RTL characters (U+0590–08FF, FB1D–FDFF, FE70–FEFF) than other letters is reversed into reading order, a character at a time. The Arabic recognizer gives the exact reverse of the text, each mark before its letter ("ًاشطع" for "عطشاً", checked on the model's output 2026-10-24). Lookupper turns it a grapheme at a time (`0x14094cc60`), which put each mark on the letter before it and moved a word's last mark onto the next word, stretching that word's box over its neighbour; Lookitan did the same until 2026-10-24. Unlike Lookupper, which reverses all of it, runs of digits and LTR words keep their order, as in PaddleOCR's `pred_reverse`, and brackets are mirrored.
  - The word trim (`trimmed` in words.rs) drops combining marks at a word's ends, as Lookupper's L*/Nd test does: Rust's `is_alphanumeric` counts Arabic harakat as letters.
  - The pop-up's headword, context, saved-card word and quote, and the Palavras fields have `dir="auto"` (or `<bdi>`), so Arabic shows right to left.
  - Arabic words run together (`segment/arabic.rs`, the `Segment` that `segment::current` returns for ar, so `pick`, `word_boxes` and `manual_candidates` use it; Lookupper has nothing like it): the recognizer misses narrow spaces ("جماعةالضفادع"). A whitespace run, trimmed as words.rs trims, that is not a word is cut into two words of at least two letters, the cut with the highest product of counts winning (counts under 500 count as 0). A word is a form seen at least 50 times in the CAMeL Arabic Frequency Lists (MSA + dialectal, counts added; `resources/hunspell/ar.words.tsv.gz`, made by `fetch-assets.py`, about 1.49 million forms, 6.3 MB, counts written only from 500) or one AyaSpell accepts (`hunspell::check`). Marks and tatweel are left out when comparing and stay with their letter. Chosen on 2026-10-24 by measuring in the scratchpad (spylls + the lists): the top-200k lists alone cut 668 of 1500 rarer real words, the 1.5M forms none of 3000; the 9 runs on the user's page are cut right, and 49 slang words stay whole. The bundled-file test in arabic.rs checks those cases in CI. The munzirtaha/ayaspell `.aff` is broken (a PFX block runs into REP), so the LibreOffice copy is used.
    - PaddleOCR (`paddle.rs` `decode_line`) reads RTL text as drawn. Lens gives words in reading order, so `lens.rs` lays them out as drawn for the ink snapping, then reverses once.
    - Characters of an RTL line run right to left on screen, so boxes take the min/max of their characters (`span_x`), and the pieces of a row in an RTL paragraph read right to left.
  - Lemmas: Lookupper has Hunspell only for de/en/es/fr/pt/ru, and uses one stem only when the word as written finds nothing (`StemAsync` `0x140243a40`, lookup `0x1402a5bb0`). Lookitan tries more forms, and has Hunspell for uk, bg, el, ar and the other languages listed under Morphology.
- **Vertical text (`OcrLine.flow`: `Across`, `Down`, `Up`):** as in Lookupper (REA on 2026-10-21), plus bottom-to-top text, which Lookupper does not read (it ships no orientation model):
  - A detected box with height ≥ 1.5 × width is read on its side: XpressOCR's test is at `0x140949830`; PaddleOCR rotates it the same way.
  - Lookupper sorts a paragraph as columns when most of its lines are taller than 1.2 × their width (`SortParagraphLines` `0x14015ed00`, with the lambda `0x14015f6c0`).
  - Lookitan:
    - `paddle.rs` `rec_crop` turns a vertical crop a quarter left (`Turn::Left`, `rotate270`), so the top of the column is at the left. `decode_line` maps the CTC steps down the column, so `OcrChar.x0..x1` are y spans on a vertical line, and `ink_y` holds its ink columns.
    - Lookitan's own additions, with no extra model:
      - A vertical box is always read as a column, however short, as in Lookupper. Reading short ones upright too (for an "I" alone) was tried and removed: upright, the squeezed 期許。 read 期 as surely as the column read 期許, and won the tie.
      - When the top-to-bottom reading scores under 0.85, the box is also read turned right (`Turn::Right`, `Flow::Up`, bottom to top, as on Portuguese book spines and chart axes).
      - Horizontal boxes and well-read columns cost nothing extra.
    - Lens spreads a vertical paragraph's letters down each word.
    - `split_focus` takes the columns beside a vertical target.
    - words.rs `upright` turns a vertical line to lie the way it reads, and all the picking, paragraphs and sentences are reused. `on_screen` turns the boxes back.
      - `Down`: top at the left, columns right to left.
      - `Up`: bottom at the left, lines left to right.
    - Lens lines from a vertical paragraph are `Down`. A line Lens gives turned a quarter is `Down` or `Up` by its words' order.
    - Lines with different flows never join in one paragraph.
- **Words of Japanese, Chinese and Korean (`segment/`, used by words.rs `pick`, `word_boxes` and `manual_candidates`):** as in Lookupper, the word under the pointer is the analyzed word holding that character, not the longest match from the pointer.
  - Lookupper (REA on 2026-10-21; addresses are in the exe with SHA-256 16af03f1…):
    - `OcrWordResegmenter.ResegmentParagraph` (`0x14015f940`) joins the paragraph's OCR words into one text, with no space between CJK characters, even across lines. It analyzes that text and rebuilds the word boxes from the words, a piece on each line for a word broken across lines.
    - The analyzers, downloaded per language into LocalState `models/`: Sudachi split mode C with SudachiDict core (`system.dic`); jieba with CC-CEDICT words added (`dict.txt`, `hmm.txt`, plus `pinyin.txt`); Kiwi (`kiwi.dll`, LGPL-2.1).
    - The Japanese chunker is `0x1401a37a0`, with its attach rule at `0x1401a3d40` and its lemma list at `0x1401a4720`. A content morpheme takes:
      - auxiliaries after a predicate;
      - 非自立 adjectives (ない);
      - て/で/ば/たり/だり, and the 非自立 verb after them or after a 連用形 verb;
      - する after a サ変 noun;
      - suffixes (名詞的 only after a noun);
      - そう/よう after a predicate.
    - Also in Japanese, a prefix takes the next morpheme, and a number its 助数詞 counter. Particles, auxiliaries alone and symbols are their own words. The lemmas are, in order: the する compound, the prefix + head, the head's dictionary form, then the surface.
    - The Korean chunker is `0x1401a1540`, with its attach rule at `0x1401a17e0` and lemmas at `0x1401a1b00`. Particles and XSN go on a nominal, endings on a verbal, XSV/XSA/VCP on a nominal, a bound noun on a number, and a VX after an EC, never across a space. The lemma is the stem + 다, the noun before 이다/아니다, or the noun (also without 들).
  - Lookitan:
    - Korean (`segment/kiwi.rs`, since 2026-10-22) is Lookupper's:
      - The analyzer is Kiwi 0.23.2 (Apache-2.0), the version in Lookupper's `models/kiwi/VERSION`, with its base (CoNg) model.
      - It is loaded at run time through its C API (`libloading`), with Lookupper's options: `kiwi_init(model, 1, KIWI_BUILD_DEFAULT, 0)` and `kiwi_analyze_w(top_n 1, KIWI_MATCH_ALL_WITH_NORMALIZING, dialect cost 3, typo threshold 2.5)`.
      - The library comes from the release's archive (Windows x64 `kiwi.dll`, Linux x86_64/aarch64 `libkiwi.so`), and the model from `kiwi_model_v0.23.2_base.tgz`. All are pinned by SHA-256 and kept in `segmenters/kiwi-0.23.2/`.
      - Morphemes are base forms with their tag (했 → 하/VV + 었/EP); a contracted syllable's morphemes share its characters. korean.rs therefore treats `start <= previous end` as written together.
      - Kiwi's `-R`/`-I` tag marks are dropped, and `W_*` tags read as SL.

- **Paragraphs (`layout.rs`):** Lookupper's layout analyzer (`0x140952880`, decoded with REA on 2026-10-21 and 2026-10-22), ported whole.
  - Pairs (`0x140959e80`): lines sorted by centre; each line with the nearest line below it that runs the same way, overlaps it across by ≥ 0.2 × the narrower width (or 3 px), and is at most 2.2 × the smaller height down.
  - Line features (`0x140953340`): words between spaces, CJK count (kana, hanzi, hangul), the first letter or digit (lower, capital, digit), a list marker (`1409536e0`: bullet, `- `, ①–⑳, `1.`/`a)` + space), and the end: sentence mark, hyphen, comma, colon, a Japanese particle or Chinese function word (`0x140953800`). Also "key: value", open brackets, all capitals, any letter, any cased letter.
  - Look (`layout::look`, `0x1409538e0`), on the capture shrunk so the median line is 20 px (0.08 to 1, INTER_AREA as Lookupper):
    - Ink (`0x140954000`): Otsu on the line's box, the smaller side is the ink. The ink height is the shortest run of rows holding 85% of it, and its colour is the mean under it.
    - Frames (`0x140954ac0`): around all lines (2.5 line heights out, shrunk to ≤ 800 px), grey, 3 × 3 median, Scharr across and down (CV_16S), absolute, added, over 40. Edge parts mostly inside the lines' boxes or shorter than 1.2 line heights are dropped. The rest, inverted and median-filtered, gives 8-connected parts. A line's frame is the part filling most of its box (parts ≥ max(16, 4 h²)), if that part holds the box; it is "filled" at ≥ 60% and "small" under half the area. These are OpenCV calls in Lookupper (REA named each P/Invoke: `imgproc_Scharr`, `imgproc_medianBlur`, `imgproc_connectedComponentsWithStats`…); Lookitan does them in Rust.
    - `OcrLine::look` holds it (`#[serde(skip)]`). `ocr_pass` measures every pass, Lens too. The background pass measures all lines again after each batch, so the frames' numbers hold.
  - Regions (`0x140956b60`): a pair is linked when the gap ≤ 1.3 h (1.8 in one small frame), the overlap ≥ 0.45 × the narrower width, the size ratio ≤ 1.35 (1.6), and they are not in two different small frames. Links make runs top to bottom, cut where a step is > 1.3 × the median step and > median + 0.3 h.
  - Region kinds (`0x1409575c0`), in this order:
    - list-like when ≥ 85% of the cased lines start with a capital or a digit (not mostly all capitals, and not `early` < 0.3 with > 3 words);
    - framed when one small frame holds ≥ 70% of its lines, no line is in another small frame, and the text spans much of it;
    - prose when ≥ half the cased lines start in lower case;
    - centred when the centres vary < 0.6 × the ends;
    - list-like when its lines are short and spaced, or most have a short line level with them in a column to the right (`0x140958740`);
    - then by `early`, the share of lines ending short whose next first word would have fitted (`0x140958a80`): ≤ 0.25 prose, ≥ 0.35 list-like, else other.
  - Score (`0x140958b50`), joined under 1:
    - adds 5 for a list marker below; 7/4/1.5 for a size ratio over 1.7/1.45/1.3 (heights or ink heights); 3/1.5 for ink colours over 100/55 apart; 3 for two different filled frames, one small; 3.5 for a step over 1.35 × the region's; 5/3/1.5 for a gap over 1.6/1.1/0.8 h; 1.5 for different regions; 5 when neither has a letter; 1.5 for a sentence end then a capital or digit (outside prose); 2 for an ending colon; 3 for two "key: value" lines;
    - by region kind and how the upper line ends (reaches the edge / wraps / would have fitted): prose 0 / −3 / +0.5; list-like +1.5 / +1 / +3, plus 2.5 when its lines start with capitals; centred −1.5; framed −2.5; other +0.5 / +0.5 / +2.5;
    - takes 4 for an ending hyphen, 2.5 for a comma, 2.5 for an open bracket, 4 for a lower-case start below, 4 for a list item's next line at its text's indent, 3 for a CJK line ending in a particle.
  - Lookitan's own on top: pieces of one row (overlap ≥ half the height, gap ≤ 1.5 h, height ratio ≤ 1.6) are one paragraph too, since Lookupper keeps a row the detector split apart.

- **Word edges (`ocr/ink.rs`), as in Lookupper's "word edges are snapped to the ink of the line":** the rules below are Lookitan's own. Lookupper's own, decoded on 2026-10-21 (REA, not ported):
  - Per line (`0x140949b60`): a line whose words are all CJK gives every character its own box, then the analyzer rejoins them. Otherwise each word is a box. Character boxes are centred on the CTC step, as wide as the mean character pitch, the full crop height; a word's box is the union of its characters'.
  - Ink (`0x14094de10`): the background is the mode of a 64-bin grey histogram (every 2nd column, 4th row). The contrast is where the outer 5% of pixels lie; it needs at least 24. A column's ink is the count of pixels further than 0.3 × contrast from the background, over the whole crop height.
  - Ink word split (`0x140950d00`, not for all-CJK or RTL lines, words of 4 to 64 characters): the blank run nearest the middle of each character pair is its gap. A word is cut where the gap is at least max(2.5 × the word's median gap, 0.75 × the line's median word gap, 0.15 × pitch, 0.25 × crop height), leaving pieces of 2 characters or more.
    - Ported on 2026-10-22: `ink::word_cuts` and `paddle.rs` `split_at_ink_gaps`, which puts a space at each cut, after `split_wide_gaps`.
    - Words there are runs of one class between spaces, CJK (`is_cjk_class`, Lookupper's `0x140950be0`) or not.
    - Only the non-CJK runs are cut; Lookupper's analyzer rejoins CJK characters across a space anyway.
    - RTL lines are left alone.
    - Lookitan's `ink.cols` count ink only in the line's ink rows, where Lookupper counts the whole crop height.
  - Snap (`0x14094da60`): between two neighbouring boxes, the best blank run within 0.4 × crop height of their meeting point (width − 1.2 × distance) becomes the boundary. The line's ends move to its first and last ink within that reach. Boxes that still overlap meet halfway (`0x14094a980`).
  - CTC gives each character only a step centre. `ink::measure` finds the crop's ink: pixels far from the median background, in the run of rows holding the most ink.
  - `ink::spans` moves each boundary between two characters to the widest blank gap between their centres, and the line's ends to its first and last ink. Spaces fill the gap between words.
  - `OcrLine.ink_y` holds the ink rows; word boxes and the pick use them (`text_rows` in words.rs).
  - Boxes keep a little room around the ink (`INK_PAD_Y` 12% of the ink height above and below, `INK_PAD_X` 8% at the sides), never past the detected line box, and neighbours that touch share the gap. Raise these two constants if the highlight still looks tight.
  - Drawn box and hit area are separate, so the tight box does not make words hard to hit. `WordBox.hit` (`OverlayWord.hit`, `[x, y, w, h]`) spans the line's whole detected height and reaches halfway to the neighbouring words, or 0.25 × line height past a line's ends. In the overlay, `.w` is that area and takes the clicks and the hover, and its `.ink` child (`pointer-events: none`) draws the highlight and the cut-out. The pointer mode never used these boxes.
  - `Pick::is_under` tests the drawn box, the same one the user sees highlighted. Before 2026-10-15 it reached a quarter of the line height past the word box, which then spanned the whole line height and half the spaces. That made the space between words and lines count as on a word, so the block outline almost never appeared.
  - With little contrast, under 40 levels, the old halfway estimates stay.
  - Google Lens lines are snapped too (`snap_to_ink` in ocr/lens.rs, since 2026-10-21): `ink::measure` on the line's box in the capture gives `ink_y`, and each word's ends move to its first and last ink column within 0.15 line heights of Lens's word box (`INK_REACH`), never past halfway to the next word. Vertical lines keep Lens's boxes.
